## 0. 你的方法论的真正形状

第一版我理解错了。我以为是「层层叠加权重」，你纠正的是：

> **「补充，但每一次结束重新完全算一遍，一步一步接近最终答案，而不是一口气算出来答案。」** ✅

这不是加权叠加，是**迭代收敛**。差别很大：

| | 叠加模型（我原来的理解，错） | 迭代收敛（你的实际做法，对） |
|---|---|---|
| 每层做什么 | 在上一层结论上打补丁 | 带着新维度**从头重算一整套完整结论** |
| 上一层的作用 | 被修改的底稿 | 参照物——用来看这一轮「改了什么」 |
| 出错的后果 | 错误会一路继承下去 | 每轮都是全新推理，前一轮的错有机会被自己纠正 |
| 结论数量 | 1 份（不断被改） | N 份完整结论，逐版逼近 |

**为什么这个区别重要：**

工程上——LLM 打补丁很容易越打越歪（它倾向于维护自己上一轮说过的话）。
**每轮强制从头重算，是在结构上防止模型自圆其说。** 这个设计比我原来那版稳健得多。

产品上——你不是产出一个结论，你是产出**一部结论的演化史**。
用户看到的是一份解读被重写 6 次、每次都更清晰。这比给一个静态答案好看太多。

### 各层性质（已确认）✅

- **V4/V5/V6（纳音/十神/神煞）是「补充」性质**——它们不推翻 V1–V3 定下的骨架（身强弱、五行盈缺、宫位），
  但它们的加入会让整套结论**重算一遍**，所以细节和侧重会变。
- **V3 权重高于 V2**，但 V2 不作废、仍参与 ✅。
  我的理解：V2 是**粗读四柱表面**，V3 是**精读日支内部**——精读优先于粗读，但粗读提供全局背景。
- **日柱坐支 = 日支藏干 ＋ 坐支关系** ✅（两者都要，不只看日支那个字）
  - 藏干：例 乙**亥** → 亥藏 壬(中气·印) 甲(本气·劫)
  - 坐支关系：乙坐亥 = 坐印；十二长生上乙在亥为「死」

## 2. reading.json —— 每一轮的输出格式

每个 Vk 吐一份**完整**结论（不是 delta），外加与上一轮的 diff：

```json
{
  "version": "V4",
  "unlockedDimensions": ["身强弱", "五行盈缺", "宫位·四柱", "日支藏干", "坐支关系", "纳音"],
  "reading": {
    "骨架": { "身强弱": "...", "五行盈缺": "..." },
    "六亲宫": { "父母": "...", "子女": "...", "配偶": "...", "亲友": "..." },
    "年龄段": [ { "range": "0-16", "claim": "...", "evidence": ["年柱 戊寅"] } ],
    "领域": { "性格": "...", "事业": "...", "财": "...", "感情": "...", "健康": "..." }
  },
  "diff": [
    { "path": "领域.财", "from": "R3 的说法", "to": "R4 的说法",
      "trigger": "日柱纳音 城头土", "why": "土能生金，补上 V1 判缺的金" }
  ],
  "conflicts": [
    { "between": ["V2·宫位", "V3·坐支"], "issue": "...", "resolution": "以 V3 为主，V2 保留为背景" }
  ]
}
```

**`evidence` 是硬性要求**：每条结论必须能指回盘里的具体证据（哪个柱、哪个藏干、哪个神煞）。
动画上点任何一句断语都要能高亮到盘上对应的位置——娱乐产品最怕「凭什么这么说」。

**`diff` 和 `conflicts` 是动画的燃料**：结论被改写的那一刻是最好看的一帧。

## 3. 这个结构对动画的直接影响 —— 两条轴

你的方法论天然给了动画**两个可拖的轴**，这比我原来设想的单一时间轴强得多：

```
                    ← 时间轴（大运 / 流年）→
    ↑        ┌────┬────┬────┬────┬────┐
  推理层     │ V1 │ V2 │ V3 │ V4 │ V5 │ V6
  （V1→V6）  └────┴────┴────┴────┴────┘
    ↓          结论演化史 —— 看着解读被重写 6 次
```

- **横轴 = 时间**：拖年份 → 关卡地图高亮跟着走（已在设计系统里做出来了）
- **纵轴 = 推理层**：拖层级 → 同一份解读的第 1 版～第 6 版之间切换，被改动的句子高亮闪烁

纵轴是别家八字 App **一定没有**的东西。它们只给你一个静态结论。
你这套方法论让产品能展示「**我是怎么想出来的**」，这是差异化的核心。

## 4. 计算量提醒（需要你知道，不用现在决定）

- 本命：6 层 × 1 次完整重算 = **6 次 LLM 调用**
- 大运完整重跑：10 步 × 6 层 = **60 次**（可以并行，但成本和延迟都实打实）
- 流年简化：约 60–100 年 × 轻量 = 可以合并批处理

合计一张盘约 **70–80 次模型调用**。不是不行，但意味着：
- 出一张完整盘大概几分钟，不是几秒 → 动画需要设计「生成中」的体验（正好，像素风的读条本身就好看）
- 结果必须缓存进 `cases/`，同一张盘不重算

如果后面觉得太重，最容易砍的是**大运从「完整 6 层」降到「V1+V3+V5 三层」**，砍掉 2/3 成本。先按你说的完整跑，跑出来看效果再决定。
